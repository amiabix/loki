# ZIP 2005 `use_qsk` FVK derivation: review request for ZF `frost` #1094

Loki (testnet-only FROST multisig wallet) derives the vault's Orchard FVK from the FROST
group key with ZIP 2005's `use_qsk = true` branch. The derivation is Loki's own code and
has not been reviewed upstream. This packet gives the exact derivation, its constants,
the vectors it matches, and the command that checks them.

Implementation: `poc/loki-signer-core/src/zip2005.rs` (66 lines),
`frost_viewing_key` at lines 39–66, `VERSION = "zip2005-use-qsk-2026.8.0"` (line 19).
The file header limits it to regtest until vectors are independently checked and the key
and backup flow is reviewed, and notes ZIP 2005 is still Proposed (lines 3–4).

## 1. Interface

```
frost_viewing_key(group_ak: &[u8;32], group_sk: &[u8;32]) -> Result<FullViewingKey, _>   // zip2005.rs:39-42
```

- `group_ak`: the FROST group verifying key, used as Orchard `ak` (`zip2005.rs:54,62`).
- `group_sk`: a 32-byte secret the group agrees on; seed for `nk` and `qsk`
  (`zip2005.rs:43,47`). In Loki it is the DKG vault secret `vs`
  (`poc/loki-signer-core/src/dkg_core.rs:643`).
- Output: `ak ‖ nk ‖ rivk` (96 bytes) parsed by `orchard::keys::FullViewingKey::from_bytes`;
  an invalid encoding returns `InvalidFullViewingKey` (`zip2005.rs:61-65`).

## 2. Derivation

```
expand_K(t, data) = BLAKE2b-512(personal = "Zcash_ExpandSeed", K ‖ t ‖ data)   // zip2005.rs:26-35

nk   = pallas::Base::from_uniform_bytes( expand_sk(0x07) ).to_repr()           // :43-44
qsk  = expand_sk(0x0c)[..32]                                                   // :47-48
qk   = blake3::derive_key("Zcash ZIP 2005 qk-derivation v1", qsk)              // :50
rivk = pallas::Scalar::from_uniform_bytes( expand_qk(0x0d, ak ‖ nk) ).to_repr() // :53-58
FVK  = ak ‖ nk ‖ rivk                                                          // :61-64
```

Both reductions are wide (64-byte input). Intermediates `expanded_nk`, `expanded_qsk`,
`qsk`, `qk`, `expanded_rivk` are zeroized after use (`zip2005.rs:45,49,51,57,59`).

## 3. Relation to `zcash-sign generate`

`poc/tests/zf_spine.rs:79-144` feeds the same `(group_ak, sk)` to `zip2005.rs` and to a
reproduction of `zcash-sign generate`'s FVK. Per that test's comment (lines 104-111),
`generate` uses orchard's `from_sk_ak_incompatible_with_quantum_recoverability_and_will_be_removed`,
i.e. `{ ak, nk: sk.into(), rivk: sk.into() }`; the test reproduces it as
`FullViewingKey::from(&SpendingKey)` with `ak` replaced by `group_ak` (lines 112-115).
Result (asserted, lines 124-137): `ak` and `nk` equal, `rivk` differs. (The default
address differing from standard Orchard's is asserted separately in
`poc/tests/zip2005_keys.rs:24-27`.)

## 5. What we ask #1094 reviewers

1. Is §2 the intended ZIP 2005 § 4.2.3 `use_qsk = true` construction: domains
   `0x07`/`0x0c`/`0x0d`, the BLAKE3 `qk` context string, `qsk` as the first 32 bytes of
   the expand output, wide base/scalar reduction, `ak ‖ nk` as the `rivk` input?
2. Are the 8 frost-tools #610 vectors correct, and can they become official vectors?
3. Will the `use_qsk` path planned for `zcash-sign` match §2, so Loki and ZF converge on
   one derivation?
