# ZIP 2005 `use_qsk` FVK derivation — review request for ZF `frost` #1094

Status: review request. Loki ships a quantum-recoverable Orchard FVK derivation for
FROST-controlled accounts (ZIP 2005 § 4.2.3, "Usage with FROST", `use_qsk = true`). The
derivation is **unreviewed upstream** — [ZcashFoundation/frost#1094] tracks exactly this.
This document gives a cryptographer reviewer the precise spec, the domain separators and
constants, the published-vector match evidence, why the construction is
quantum-recoverable, and how it differs from `zcash-sign generate`'s current
non-recoverable constructor.

Implementation under review: `poc/src/zip2005.rs`
(`VERSION = "zip2005-use-qsk-2026.8.0"`). It is the only Loki-owned crypto derivation in
the real-funds path; everything else is the audited `frost-core` /
`frost-rerandomized` / `reddsa` / `orchard` stack.

---

## 1. Inputs and output

```
frost_viewing_key(group_ak: [u8;32], group_sk: [u8;32]) -> FullViewingKey   // 96 bytes
```

- `group_ak` — the FROST group verifying key, used directly as the Orchard spend
  validating key `ak`. A valid FROST group key has `ỹ = 0`, i.e. `group_ak[31] & 0x80 == 0`.
- `group_sk` — a 32-byte secret the group agrees on (out of band to this derivation). It
  is the seed for `nk` and for the quantum-recovery key material.
- Output `FVK = ak ‖ nk ‖ rivk` (32 ‖ 32 ‖ 32), parsed by `orchard::keys::FullViewingKey::from_bytes`.

## 2. Derivation (exact)

```
nk   = ToBase ( PRF^expand_sk ( [0x07] ) )                      // Pallas base field
qsk  = truncate_32 ( PRF^expand_sk ( [0x0C] ) )                 // first 32 of 64 bytes
qk   = BLAKE3.derive_key ( "Zcash ZIP 2005 qk-derivation v1", qsk )
rivk = ToScalar ( PRF^expand_qk ( [0x0D] ‖ ak ‖ nk ) )          // Pallas scalar field
FVK  = ak ‖ nk ‖ rivk
```

Where:

- `PRF^expand_K(t)` is BLAKE2b-512 with personalization `"Zcash_ExpandSeed"` (16 bytes),
  hashed over `K ‖ t` (`poc/src/zip2005.rs:26-35`). This is the standard Zcash
  `PRF^expand` used throughout ZIP 32 / Orchard.
- `ToBase` = `pallas::Base::from_uniform_bytes` over the full 64-byte BLAKE2b output
  (wide reduction into the Pallas base field) (`zip2005.rs:44`).
- `ToScalar` = `pallas::Scalar::from_uniform_bytes` over the 64-byte output
  (`zip2005.rs:58`).
- `truncate_32` takes the first 32 bytes of the 64-byte expand output (`zip2005.rs:48`).
- `BLAKE3.derive_key` is `blake3::derive_key(context, key_material)` (`zip2005.rs:50`).

### Constants / domain separators

| Name | Value | Role | Source |
|---|---|---|---|
| expand personalization | `b"Zcash_ExpandSeed"` | BLAKE2b personal for `PRF^expand` | `zip2005.rs:12` |
| `NK_DOMAIN` | `0x07` | `PRF^expand_sk` tag for `nk` | `zip2005.rs:14` |
| `QSK_DOMAIN` | `0x0C` | `PRF^expand_sk` tag for `qsk` | `zip2005.rs:15` |
| `RIVK_EXT_DOMAIN` | `0x0D` | `PRF^expand_qk` tag for `rivk` | `zip2005.rs:16` |
| `QK_CONTEXT` | `"Zcash ZIP 2005 qk-derivation v1"` | BLAKE3 derive-key context for `qk` | `zip2005.rs:13` |

All secret intermediates (`expanded_nk`, `expanded_qsk`, `qsk`, `qk`, `expanded_rivk`)
are `zeroize`d after use (`zip2005.rs:45,49,51,57,59`).

## 3. Why it is quantum-recoverable

Standard (non-FROST) Orchard derives `rivk = sk.into()` directly from the spending key
(`rivk` is a fixed function of `sk`). ZIP 2005 § 4.2.3 instead routes the
randomized-issuance viewing key through a **separate** key `qk`:

```
qsk  ⟵ sk          (an independent expand branch, tag 0x0C)
qk   ⟵ BLAKE3.derive_key(context, qsk)
rivk ⟵ expand_qk(0x0D ‖ ak ‖ nk)
```

Because `rivk` is bound to `qk` (hence to `qsk`), and `qsk` is a distinct expand branch
of `sk`, the holder of `sk` can **re-derive the full viewing key deterministically** —
including after a migration that would otherwise break the classical `sk → rivk`
relationship. This is the "quantum recoverability" property ZIP 2005 is about: the
viewing capability survives because it is reconstructible from the agreed secret via a
fixed, hash-based path, rather than being a one-shot artifact of key generation. `nk`
remains `expand_sk(0x07)` — identical to classical Orchard — so the nullifier key is
unchanged; only the `rivk` path differs.

## 4. Difference from `zcash-sign generate` (non-recoverable)

`frost-tools/zcash-sign/src/generate.rs` (ZF tooling, `frost-tools@53df99c`) does **not**
use this path. It draws a **random** `sk` per call and builds the FVK with
`FullViewingKey::from_sk_ak_incompatible_with_quantum_recoverability_and_will_be_removed`.
In `conradoplg/orchard@42015f1` (`src/keys.rs`, the orchard `zcash-sign` builds against)
that constructor is literally `FullViewingKey { ak, nk: sk.into(), rivk: sk.into() }` —
the plain Orchard derivation, with **no `qk` / BLAKE3 / `use_qsk` step**. The
constructor name and `frost-tools#591` state the intent to remove it; quantum
recoverability is deferred there.

Consequence, confirmed by a fixed-`(group_ak, sk)` byte comparison in
`poc/tests/zf_spine.rs` (documented in `docs/product/ADOPTION.md` §3):

| FVK segment | zip2005 (`use_qsk`) | `zcash-sign generate` (non-recoverable) | Match |
|---|---|---|---|
| `ak`   `[0..32]`  | from FROST group key | from FROST group key | = |
| `nk`   `[32..64]` | `expand_sk(0x07)` | `sk.into()` | = |
| `rivk` `[64..96]` | `expand_qk(0x0D ‖ ak ‖ nk)` | `sk.into()` | **≠** |

Same `nk`, different `rivk` ⇒ different `ivk` ⇒ **different vault address**. The two
derivations are not interchangeable; `zcash-sign generate` cannot replace the
recoverable path without changing the address members scan. (It also cannot reproduce a
fixed FVK for a fixed group key, since its `sk` is random.) This is why Loki keeps
`zip2005.rs` and brings it here for review rather than adopting `generate`.

## 5. Vector-match evidence

### 5.1 Vectors

The reference vectors are the 8 published in **ZcashFoundation/frost-tools PR #610**
("test(zcash-sign): add ZIP 2005 use_qsk key derivation vectors", branch
`test/zip2005-use-qsk-vectors` on the `zafe-cash` fork, commit
`038204d4ff1f58042c54ce55be02336c77e703c6`), file
`zcash-sign/tests/fixtures/zip2005_use_qsk.json`. Each vector gives `(sk, ak)` and the
derived `nk`, `qsk`, `qk`, `rivk_ext`, the 96-byte FVK, the default address and an
Orchard-only testnet UFVK. Per the PR, these are **not yet official vectors** — they are
generated by `zafe-core` and independently recomputed by a stdlib Python script — which
is precisely the gap #1094 asks to close with upstream review.

The fixture is committed verbatim at `poc/tests/fixtures/zip2005_use_qsk.json` with its
provenance recorded in `poc/tests/zip2005_vectors.rs`.

### 5.2 Durable test

`poc/tests/zip2005_vectors.rs` feeds each vector's `(ak, sk)` into Loki's
`frost_viewing_key` and asserts the published 96-byte `fvk` byte-for-byte, plus the
structural invariants (`ak` preserved, `nk` and `rivk` at the expected offsets). The
BLAKE3 `qk_context` string in the fixture is also pinned to the constant in
`zip2005.rs`.


All 8 published `use_qsk` vectors match Loki's `zip2005.rs` output exactly.

A second, independent corroboration pre-exists in `poc/tests/zip2005_keys.rs`: two

reduction) implementation, which also pass. Note vector #1 of the published set

`zip2005_keys.rs` second vector built from the same `sk` — the two independent sources
agree.

## 6. What we ask #1094 to review

1. That the derivation in § 2 is the intended ZIP 2005 § 4.2.3 `use_qsk` construction
   (domains `0x07` / `0x0C` / `0x0D`, the BLAKE3 `qk` context string, wide
   base/scalar reduction).
2. That the 8 vectors in § 5 are correct, with a view to promoting them to **official**
   test vectors upstream.
3. Any divergence between this and the `use_qsk` path intended for `zcash-sign generate`
   once recoverability is un-deferred, so Loki and ZF converge on one derivation.
