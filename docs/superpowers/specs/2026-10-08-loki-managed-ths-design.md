# Loki-managed THS demo design

## Purpose and agreed choices

The Loki browser demo will start and manage its own disposable THS regtest
environment. Users will not need to start THS separately. Loki will retain its
step-by-step account, scan, proposal, approval, and execution flow.

The user has selected a dedicated Loki-owned instance and requires deletion with
`ths --name <instance> stop` when the demo stops. Closing or refreshing a browser
tab will not stop the network; the Python demo server owns its lifecycle.

## Reviewed evidence

- `zcashlabs/zcash-skills`, revision
  `a351f76fab35e0f09d52c15428348ae3062e156d`, including the THS runtime, wallet-server,
  and live-verification guidance.
- Loki's `poc/demo/runner.py`, `poc/run-ths.py`, `poc/THS-RESULTS.md`, and
  `poc/THS-ISSUES.md`.
- Installed launcher help and version: `ths 0.3.0` supports named instances,
  `start --no-open --port-offset`, endpoint discovery, mining, and stop.
- Neighboring THS source revision `789b7bb`, including resource ownership checks,
  start/stop lifecycle, and external-address faucet processing. That source is
  navigation evidence, not proof of the installed launcher's or app image's behavior.

The upstream skills contain newer resource-ownership guidance than Loki's local
copy. Their description of the external-address faucet is older than the
neighboring THS source, which persists requests and transaction identity.
Neither a version string nor an idempotency field alone establishes retry safety
for the installed app. Integration validation must identify the actual artifacts.

## Browser flow

1. Create the account locally using the existing Loki setup operation. THS is not
   needed to create the FROST shares or test-only vault address.
2. Start test network checks for the Loki binary, installed `ths`, Docker access,
   and usable runtime images. It creates a unique instance name for this run,
   records it in the sandbox, selects an available THS port offset, and starts
   `ths --name <instance> start --no-open --port-offset <offset>` as a managed child.
   Docker and THS must already be installed; this operation does not install or
   upgrade software. First-run image acquisition may take time and must be visible.
3. Discover endpoints through `ths endpoints --json`. Validate loopback endpoints,
   the selected instance, regtest, the NU6.3 activation and consensus branch required
   by Loki, and live service readiness. Endpoint metadata alone is insufficient.
   Check current wallet-sync readiness before faucet use, rather than relying only
   on HTTP 200 from the health endpoint.
4. Fund the vault with two 100,000,000-zatoshi notes through the external-address
   faucet, preserving the alternate-input security drill. Persist a separate
   request identity for each note and the run's funding state. Record the
   transaction and confirmed block when available. Network readiness and funding
   readiness are distinct, so funding failure does not label a healthy network down.
5. Keep scan as an explicit step. Loki's own scanner determines the vault balance
   from the chain. THS's user-account balances are not the Loki vault balance.
6. Keep nonce commitments, proposals, member review/signing, and proof construction
   in Loki. Every chain-facing CLI invocation uses the discovered RPC endpoint and
   clears inherited configuration that could select another signing round.
7. Execute broadcasts through Loki, mines through `ths --name <instance> mine`,
   checks inclusion, and runs `verify-effects` against the approved intent. Broadcast
   acceptance alone is not a completed payment.

Repeated Start requests while the assigned instance is healthy do not recreate
its chain or repeat funding. A single operation lock prevents overlapping startup,
funding, execution, and reset operations.
An advisory server lock prevents two processes from owning the same sandbox.

## Funding failures and retries

The installed app's external-address faucet contract will be verified before
automatic retries are enabled. A saved idempotency key will be reused only when
the actual artifact supports replay of the same persisted payment.

An HTTP timeout is an unknown result. Record that state and reconcile the original
transaction or scan the fresh vault for the intended funding before constructing
another request. If the result cannot be established and replay safety has not
been verified, show funding as uncertain and require a fresh disposable run rather
than automatically requesting another payment.

## Ownership, ports, and lifecycle

Instance identity is generated by the server, never supplied by a browser request.
Use a fresh name per run and refuse existing resources with that name before
launching: `ths start` prepares a fresh environment and must not be used as a
generic attach operation. Record enough identity to distinguish this demo's run
from unrelated THS environments. Verify resource ownership before cleanup using
the behavior of the actual launcher and recorded resource identities.

Select a valid available THS port offset in multiples of ten, checking the complete
published-port set. Discover the actual dashboard and RPC endpoints afterward.
Handle allocation races as startup failures, cleaning only the selected owned
instance. Reset creates a fresh allocation for a subsequent attempt. All host
bindings stay on loopback.
The earlier standalone-node change to port 18252 becomes obsolete when the browser
runner is migrated to discovered THS endpoints.

Stop test network, reset, normal server exit, SIGINT, and SIGTERM use one cleanup
path. Cancel or settle any in-flight operation so it cannot fund, mine, or recreate
resources after cleanup begins. Invoke `ths --name <instance> stop`, verify the
owned Docker resources are gone, and then terminate and reap the managed foreground
launcher process if it is still waiting. Do not rely solely on killing that process.

Partial startup failure uses the same scoped cleanup. If cleanup fails, retain
the ownership manifest, show the error, and permit retrying cleanup. Do not report
successful deletion or erase recovery information while resources remain.

Forced termination cannot execute shutdown hooks. On the next demo-server start,
inspect a retained ownership manifest and recover cleanup of that run before
starting a replacement. Never delete an environment based solely on a generic
name or port, and never prune shared Docker resources.

## Run state and interface

The UI exposes stopped, starting, running, stopping, and failed network states,
with a separate funding state including funding, confirmed, failed, and uncertain.
Display the assigned instance and live block height; diagnostic views may show
the discovered endpoints and startup logs. Refreshes read server state and do not
trigger operations. A crashed child or failed live readiness check updates the UI
instead of leaving a stale running indicator.

Stopping deletes the chain and ends the run. Retain local artifacts for inspection,
but mark their network ended and disable scan, proposals, approvals, and execution
against a replacement chain. Require the existing explicit sandbox reset before
starting a fresh account and network. Reset deletes only the fixed Loki sandbox
after THS cleanup succeeds. Recorded artifacts alone must not mark a deleted
network running or a fresh network funded.

## Scope and implementation ownership

Loki's Python runner owns orchestration. A focused THS helper can own subprocess
lifecycle, endpoint discovery, faucet calls, and mining while the existing runner
continues to own stage sequencing and account artifacts. Preserve standard-library
Python and the fixed request allowlist; do not accept arbitrary commands, paths,
instance names, endpoints, or flags from the browser.

Update the browser's state rendering and setup text, demo documentation, and the
README distinction between the managed browser flow and standalone CLI harnesses.
Remove the browser runner's dependency on `poc/harness/zebrad`; keep standalone
shell harnesses available. THS manages its Docker and launcher metadata outside
the Loki sandbox, so revise the old one-writable-directory claim accurately.

The target is integration with installed THS, not changes to THS crates, images,
or releases. If an installed artifact lacks a required ownership or payment
guarantee, report the compatibility gap before expanding scope. THS supplies the
chain, faucet, and mining; Loki remains responsible for threshold signing,
scanning, and proofs. The test-only vault construction and other documented
prototype limitations remain unchanged.

## Validation

- Deferred runner tests will cover repeated Start, unavailable prerequisites, occupied ports,
  delayed readiness, exited launcher, partial startup, uncertain faucet response,
  cleanup failure, and retained ownership information.
- Deferred browser regression tests will cover startup progress, distinct running/funding
  states, errors surviving reload, actual endpoint display, and ended-run controls.
- A live disposable THS run covers account setup, automatic startup, funding,
  Loki scanning, proposal, signing, proof/broadcast, mining, and effects verification.
- Exercise stop, reset, and server interruption. Verify absence of the selected
  instance's containers, volumes, and network, and verify that the preexisting
  `loki-poc-20261008` environment retains its original resource identities.
- Record the launcher and image identities exercised. Distinguish mocked logic
  checks from live Docker evidence and report browser engines actually run.

## Design review

Dedicated ownership and shutdown through `ths stop` are approved. This document
records the approved flow. The user authorized implementation in the existing
`loki-ths-migration` worktree and explicitly deferred test authoring until later.
