# Separate-member setup experiment

`loki_setup_member` runs a 2-of-3 FROST DKG in three processes, each with its own member directory. The group key is real. Each process derives the same viewing key using ZIP 2005's `use_qsk = true` branch. This derivation is local and unreviewed; the address remains **regtest-only**. Each member makes and checks a backup before the ordinary address command will show it. The resulting member state is used by `loki_member_payment` for a regtest payment.

## Reproduce

```sh
cd poc
cargo test --test setup_processes
cargo test --test distributed_setup
cargo test --test setup_transport
```

The process test creates three owner-only stores, a public exchange directory, and a roster. It starts three `loki_setup_member run` processes concurrently, checks that no address is printed, then requires all three members to check their cards before the address command succeeds. It builds an unproved Ironwood candidate for the resulting ZIP 2005 vault, serializes and parses that candidate, checks its payment effects, and signs its actual sighash using two shares loaded from the member stores. The signature verifies under the candidate's randomized spend key. This uses a synthetic note offline; it does not prove, broadcast, or mine a payment. The test restores each member's sealed state from the card and words, including once with the exchange directory removed. A wrong roster fingerprint is refused before any DKG message is published.

## Manual ceremony

1. On each member's machine, choose a member directory outside the source checkout and create a passphrase file readable only by that member (`chmod 600`). Run `loki_setup_member identity <member-dir> <id:1|2|3> <passphrase-file>` and share only its JSON output. The private identity is stored as `secrets/identity.sealed`.
2. Build one JSON roster with a fresh random 32-byte hex `vault` (for example, `python3 -c 'import secrets; print(secrets.token_hex(32))'`) and a `members` array containing all three public identity JSON objects. Give the identical roster file to each member. Run `loki_setup_member fingerprint <roster.json>` on all three machines and compare the result by a trusted call or group chat.
3. Each member starts `loki_setup_member run <member-dir> <passphrase-file> <roster.json> <exchange-dir> <agreed-fingerprint>`. Keep all three processes running until completion. Deliver files from each process's exchange directory to the others without editing them. A shared folder works for a local drill; on separate machines the courier must copy complete files atomically. If a process exits or any check fails, discard that vault id and begin again with a new roster and exchange directory.
4. Each member runs `loki_setup_member backup-create <member-dir> <passphrase-file> <new-card-dir>`. It writes `<new-card-dir>/vault.card` and prints 24 words once. Keep the words separately from the card. Put the words in an owner-only file (`chmod 600`) and run `loki_setup_member backup-verify <member-dir> <passphrase-file> <card-dir> <words-file> <roster.json> <exchange-dir>`. This reopens the card and publishes that member's signed confirmation. The printed words can appear in terminal scrollback; clear it after storing them.
5. Once all three confirmations have arrived, `loki_setup_member address <member-dir> <passphrase-file> <roster.json> <exchange-dir>` checks them and shows the regtest address. A missing or altered confirmation is refused. The successful check is sealed locally; later `loki_setup_member address <member-dir> <passphrase-file>` works without the exchange. To restore without any relay or exchange directory, run `loki_setup_member restore <new-member-dir> <new-passphrase-file> <card-dir> <words-file>`; it writes a new sealed member state and prints the derived address. The new passphrase protects local storage and is not a third backup artifact.

Round-one messages, final certificates and backup confirmations are signed. Round-two DKG shares are signed and encrypted to one recipient. The group certificate binds the DKG transcript, group key, public package, shared vault-secret derivation, key-derivation version and roster fingerprint. Each member writes only its own signing share in one atomic `secrets/vault.sealed` file, sealed under its passphrase. The backup card is an encrypted copy of that versioned regtest state, including the member's identity key and the shared viewing secret, sealed with Argon2id and XChaCha20-Poly1305 under the 24 words. Anyone with both artifacts can read the vault's history but cannot spend alone. Setup on the same member directory is locked so two processes cannot replace each other's state. The CLI's fingerprint check is effective only if members actually compare it out of band.

The existing `loki setup` path remains a mined transaction regression fixture and still uses a test-only viewing key. `loki_setup_member` rejects older state files without the ZIP 2005 derivation marker and verifies its stored address and key packages when reopened. The card format and key derivation still need independent review. `loki_member_payment` connects the activated member state to proposal review, FROST signing, independent finishing and a mined regtest payment; see [Signing sessions](SIGNING-SESSION.md). This is **not** a spendable user wallet: the old simultaneous command uses a local courier and RAM-only nonces; the staged relay-backed command has a conditional rollback defense but no browser custody boundary.
