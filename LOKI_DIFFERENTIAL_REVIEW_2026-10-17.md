## Findings

### 1. High release blocker: Testnet proposals fail at the relay manifest parser

**Code:** `poc/src/payment_manifest.rs:84-96,169-184`, `poc/src/bin/loki_relay_member.rs:470-490,535-543` on `feat/ironwood-wallet-store` (same inherited behavior in the earlier Testnet branches). **Affected callers:** `send-proposal`, `import-proposals`, and proposal filtering during signing-message export; the member app calls `send-proposal` from `sync_payments` at `poc/wallet/member_app.py:1486-1494`.

`parse_for_network` supports Testnet, but the public `parse` helper always selects Regtest. Both `encode_proposal` and `decode_proposal` call `parse`, and `send_proposal` calls it before encoding. A Testnet draft generated by `loki_member_payment prepare` has `"network":"testnet"` (`poc/src/bin/loki_member_payment.rs:291-300`), so `send-proposal` rejects it at the first parse with `unsupported payment manifest`. A received Testnet proposal is rejected for the same reason. This prevents the advertised relay-backed Testnet payment path from starting; it does not by itself expose funds.

**History:** `parse(raw)` entered with the original regtest-only relay proposal flow in `0b09b00`. Testnet support added `parse_for_network` without updating these relay call sites. Existing manifest tests cover regtest proposals only; there is no Testnet send/import test in the reviewed stack.

**Fix:** Open the member session first, then parse and encode against its certified `member.network`; pass that expected network through proposal decoding and import. Add a Testnet proposal round-trip test and a relay send/import test that includes an authenticated Testnet roster. Keep rejection of a mismatched network.

### 2. Medium safety regression: pending-note reservation is absent from the new stack

**Code:** `poc/src/bin/loki_member_payment.rs:220-276` on `feat/ironwood-wallet-store`; reference fix `1e2e7c2` on `security-triage-bot`. **Affected callers:** member-app payment draft creation and direct payment CLI preparation.

The newer `prepare` scans chain notes and selects a covering note without checking this member's saved, unexpired proposals or serializing concurrent prepares. Two rapid drafts can therefore select the same nullifier. Only one conflicting spend can mine; the other payment attempt must be recreated. All five locally visible target refs (`origin/main` and the four feature branches) lack commit `1e2e7c2` by ancestry. This is an **integration gap between independent branches**, not a regression introduced by the wallet-store commit alone.

**Fix:** Adapt the reservation behavior and its draft-to-final-directory test to the new network and threshold-aware payment code, then test two concurrent local drafts. Integration requires the owner's explicit direction under this repository's worktree rules.

## Storage boundary and test coverage

The new wallet store derives a SQLCipher key with Argon2, checks `cipher_version`, verifies vault viewing key and birthday on reopen, and creates a new database with owner-only mode (`poc/src/wallet_store.rs:177-255`). Three integration tests cover encrypted reopen, persisted scan height, and an Ironwood note with a witness (`poc/tests/wallet_store.rs`). The sync command enforces HTTPS except loopback and checks the reported Testnet chain name (`poc/src/bin/loki_wallet_sync.rs:12-78`). These are useful safeguards; they do not establish that a live public lightwalletd sync and spend path works. The birth tree state comes from the same lightwalletd endpoint, so the displayed balance inherits that endpoint's chain-data trust assumption.

## Review method and limits

I used commit ancestry, per-commit diffs, call-site search, and line-by-line tracing of the proposal, note-selection, and wallet-store paths. The proposal failure follows deterministically from the network comparison in source. No feature-branch test suite or live Testnet payment was run, and GitHub PR/CI state was not available. Confidence is high for the two findings and limited for the rest of the large feature stack. No other worktree was edited or integrated.

### Active local-chain indexer branch

The newly created `speedmaster` worktree switched to `feat/local-chain-indexer` at 07:00 PDT and has an uncommitted `poc/src/bin/loki_indexer.rs`. It exposes `scan::scan_chain_cached` with a caller-selectable cache path. The cache previously stored chain position and the first vault's selected actions without recording which viewing key selected them. Reusing a cache created by a vault with no notes on that chain for a second vault made the second vault's scan return zero notes without reading earlier blocks.

I reproduced this with a failing regression test (`0` notes instead of `3`), then committed a shared-code fix on `security-triage-bot` as `a297f0c`. It saves a domain-separated hash of the viewing key with the cache and resets unbound or different-key cache state before scanning. All 74 library tests passed, including the new test and the existing reorg tests. The active indexer worktree was not edited or integrated; it still needs this fix before using shared or caller-supplied cache paths.
